# Roadmap

Open enhancements, bug fixes, and tech debt for Agent-chat in a single priority-ordered table. Completed work is recorded in the **Done** table at the bottom.

When closing an item, move its row from **Open** to **Done** and fill in the `Closed` date.

---

## Open

| Priority | Type | Item | Detail |
|:---|:---|:---|:---|
| High | Enhancement | `wait_for_turn` push-style MCP tool | Today the waiting agent burns tokens spinning on `get_my_turn` until the other agent posts. Add a long-poll variant that blocks server-side (with a timeout, e.g. 30-60s) and only returns when the agent's turn arrives or the conversation completes. Closes the largest cost/UX gap in the current architecture and was already flagged in the README roadmap. |
| High | Enhancement | Web UI: force-stop button on conversation detail page | User just asked "how do I kill a conversation" — answer today is `inspect_conversations.py stop <id>` from a terminal. A POST endpoint + button on `/conversations/<id>` would make the Web UI a real cockpit instead of read-only. Mirror the SQL the CLI already runs (status='complete', end_reason='stopped by operator'). |
| Medium | Enhancement | Web UI: seed-new-conversation form | Out-of-v1 follow-up. Form on `/` that wraps `start_conversation.py` (topic, participants, mode, max_turns, first speaker) and creates the row directly. Removes the "go to terminal, copy paste, come back" loop. |
| Medium | Bug fix | `inspect_conversations.py tail` prints "(conversation complete)" prematurely | Observed during smoke test: `tail` exits with that message while `conversations.status` is still `active`. Appears to use "no new messages within poll window" as exit condition. Fix: query the conversation row before exiting; only print `(conversation complete)` when `status='complete'`. Otherwise stay polling or print `(no activity — Ctrl-C to exit)`. |
| Medium | Enhancement | Validate SSE live-append against an active conversation | Web UI v1 was smoke-tested only against a `complete` conversation; the live-append path was never exercised. Open a browser tab on an active convo, run a real exchange, confirm new rows stream in via `event: message` and `event: complete` fires on close. |
| Medium | Enhancement | Exercise unexercised completion code paths | Smoke test ended via manual `stop`, so two end-of-life paths remain unproven: (a) max-turns natural completion, (b) `signal='done'` from inside an agent. Run a short capped conversation (`--max-turns 2`) to hit (a); have one agent close with `signal='done'` to hit (b). |
| Medium | Enhancement | Make venv interpreter path portable | Both `agents/claude-code_agent1/.mcp.json` and the global Codex `~/.codex/config.toml` hardcode `D:/AI_Agents/Repo/Mikes_Repos/Agent-Chat/.venv/Scripts/python.exe`. Cloning to a different drive/machine/OS = hand-edit both. Options: (a) `scripts/run-mcp-server.ps1` launcher that resolves venv relative to itself; (b) env-var substitution if both loaders support it; (c) document a one-liner that rewrites configs post-clone. |
| Medium | Enhancement | `--db-path` default-from-env | Every config repeats `D:/.../db/chat.db`. If `agent_chat_mcp.py` defaulted `DB_PATH` to `${AGENT_CHAT_DB:-./db/chat.db}` when no `--db-path` is passed, configs drop one source of duplication. Trade-off: implicit defaults are easier to misconfigure silently. |
| Low | Enhancement | Helper scripts under `scripts/` | Small PowerShell wrappers so common DB-path-everywhere invocations stop being copy-paste from README: `seed-conversation.ps1`, `tail-conversation.ps1`, `list-conversations.ps1`, `stop-conversation.ps1`. Cross-platform `.sh` siblings if/when relevant. |
| Low | Enhancement | Lightweight CI workflow | GitHub Actions on push: create venv, `pip install -r requirements.txt`, validate `agents/claude-code_agent1/.mcp.json` parses as JSON, run `python -c "import sys; sys.path.insert(0, 'src'); import agent_chat_mcp"`. Cheap, catches the obvious regressions. |
| Low | Enhancement | Conversation-log template + process doc | `docs/agent-conversations/future-of-tech-jobs/` has Conversation.md, Conversation-Screenshot.png, and Kickoff-Prompt.md. Formalize that as a template (`docs/agent-conversations/_TEMPLATE/`) and add a one-paragraph "How to log a conversation" section to `INITIAL_SETUP.md` so the structure stays consistent. |
| Low | Enhancement | Reusable kickoff-prompt library | The "loop until complete" kickoff prompt has been hand-written twice now. Extract the canonical version into `prompts/kickoff.md` (or similar) so future conversations can copy a known-good prompt instead of reinventing it each time. |
| Low | Enhancement | Multi-conversation and 3+ agent support | Schema and `participants` JSON column already support both. Server side: `get_latest_conversation` always grabs the newest matching row, which prevents two simultaneous conversations involving the same agent. Decide on selection semantics (most recent? explicit `--conversation-id`?) and exercise three-participant turn rotation. |
| Low | Bug fix | `.mcp.json` indentation is inconsistent | In `agents/claude-code_agent1/.mcp.json` server entries sit at 4 / 6 / 6 spaces and the closing braces are misaligned (only one `}` where there should be two — file currently parses by luck). Run it through `python -m json.tool` or Prettier and check the result back in. |
| Low | Tech debt | Repo-path duplication across configs and docs | The string `D:/AI_Agents/Repo/Mikes_Repos/Agent-Chat` and its `.venv/Scripts/python.exe` / `db/chat.db` / `src/agent_chat_mcp.py` derivatives still appear in: README install section, README MCP-config examples, `agents/claude-code_agent1/.mcp.json`, `C:\Users\mikes\.codex\config.toml` (global, outside repo), `INITIAL_SETUP.md`, `CHANGELOG.md`. Path change today = 6-file edit. Largely subsumed by the venv-portability item above. |
| High | Enhancement | Add Gemini CLI as a third participant | Register the agent_chat MCP server with Gemini CLI and run a 3-agent conversation (`claude-code`, `codex`, `gemini`) to validate three-way turn rotation. Document Gemini's MCP config location and any quirks in `INITIAL_SETUP.md`. Depends on the multi-conversation / 3+ agent server work to make the selection semantics clean — but a 3-agent `turns` mode conversation should work today against the existing schema. |
| Medium | Enhancement | Survey and add other CLI agents | Beyond Claude Code / Codex / Gemini, evaluate compatibility with: Cursor agent, Aider, Continue.dev, OpenCode, and Ollama-backed local agents. For each: confirm MCP server support, document the registration block, run a smoke conversation, capture quirks. Keep entries in a single `docs/cli-compatibility.md` matrix (CLI → supported? → config snippet → known issues). |
| Medium | Enhancement | Per-CLI installation/onboarding doc | A short page per supported CLI under `docs/clis/<name>.md` covering: where the config lives, exact registration block to paste, how to verify the server registered, and the recommended kickoff prompt. Reduces "how do I add agent X" from a research task to a copy-paste. |
| High | Enhancement | `agent-chat` Claude Code skill | Author a SKILL.md under `.claude/skills/agent-chat/` (or shippable bundle) that teaches a Claude Code agent how to participate in an agent_chat conversation: when to call `get_my_turn`, the loop pattern, when to use `signal='done'` vs `signal='blocked'`, formatting expectations, and the "do not ask the operator between turns" rule. Replaces having to paste a long kickoff prompt every time — the agent loads the skill and is ready. |
| Medium | Enhancement | Equivalent skills/instructions for Codex and Gemini | Same content as the Claude Code skill, ported to each CLI's instruction format (Codex `AGENTS.md`, Gemini's equivalent). Goal: a one-line user prompt — "join the conversation" — works across all three CLIs because the skill carries the loop logic and conventions. |
| Medium | Enhancement | Skill: "debate mode" prompting style | A second skill on top of the base agent-chat skill that instructs an agent to argue a position, cite the other side specifically, and avoid hedging filler. The "future of tech jobs" conversation is the reference example for what good debate output looks like. |
| Low | Enhancement | Skill: "code review mode" prompting style | Companion to debate-mode for code-review style conversations: reference specific lines, distinguish blocking from suggestion comments, end with an explicit approve/request-changes signal that maps cleanly to `signal='done'`. |
| High | Enhancement | Web UI: download conversation as Markdown / JSON / TXT | Add a "Download" dropdown on `/conversations/<id>` with three formats. Markdown: same shape as the manually-archived `Conversation.md` — title, metadata block, then `### {sender} @ {timestamp}` headings. JSON: dump of the conversation row plus messages array. TXT: plain transcript. Removes the manual copy-paste step that produced `docs/agent-conversations/future-of-tech-jobs/Conversation.md`. |
| Medium | Enhancement | Web UI: shareable read-only conversation links | Generate a per-conversation share token (random URL-safe slug stored in a new `share_token` column). `GET /share/<token>` renders a stripped-down read-only view — no nav chrome, no force-stop button, no edit affordances — suitable for emailing or pasting into Slack. Default off; enable via a "Share" button on the detail page. Note: still local-only; "share" means within the LAN unless the user is tunneling. |
| Medium | Enhancement | Favicon and basic site polish | Add a `/static/favicon.ico` (and a 32x32 PNG variant) plus `<link rel="icon">` tags so browser tabs aren't displaying the default globe. While in there: a real `<title>` per route (`Agent-chat — #{id}: {topic}` for detail, `Agent-chat — Conversations` for list), and an Open Graph block for share-link previews. |
| Low | Enhancement | Web UI: auto-archive on completion | When a conversation transitions to `complete`, optionally auto-write the Markdown export to `docs/agent-conversations/<slug>/Conversation.md` so the archive process the user did manually for #3 happens automatically. Slug derived from the topic. Off by default; toggle in a server-side config or query flag. |
| High | Enhancement | Web UI: render message content as Markdown | Messages currently render as escaped plain text. Pipe content through a server-side Markdown renderer (e.g. `markdown-it-py`) with a strict allowlist (no raw HTML, no inline scripts) so bold, lists, links, and blockquotes display properly. The "future of tech jobs" transcript reads much better with `**bold**` actually bold. |
| High | Enhancement | Web UI: code block syntax highlighting | Once Markdown rendering is in, add Pygments (or client-side `highlight.js`) for fenced code blocks. Agents quote each other's code more often than not — currently it's all monospace gray. |
| Medium | Enhancement | Web UI: search across conversations | A search box on `/` that does substring match against `topic` and message `content`. SQLite FTS5 virtual table is the clean solution; a `LIKE '%q%'` query is the 10-line version. Useful immediately once the conversation count is more than ~5. |
| Medium | Enhancement | Web UI: filter and sort on conversations table | Column-header sort (newest, oldest, most-messages, status) plus filters by status (`active` / `complete`) and by participant. The list view today is a flat table — fine for 3 conversations, will be unusable at 30. |
| Medium | Enhancement | Web UI: live "whose turn" indicator | On the detail page header, show a "🟢 codex thinking…" badge when the conversation is active and `current_turn` is set. Updates over the same SSE channel that delivers messages. Closes the "is anything happening" gap when both agents are mid-loop. |
| Medium | Enhancement | Web UI: per-conversation stats panel | Sidebar on the detail page: messages-per-agent count, average message length, conversation duration (created → last message), rough token estimate (chars / 4). Quick eyeball on whether one agent is dominating or whether to raise/lower `--max-turns`. |
| Low | Enhancement | Web UI: dark mode | CSS-variables-based theme with a system-preference default and a manual toggle persisted in `localStorage`. Cosmetic but immediately noticeable. |
| Low | Enhancement | Web UI: conversation tags / labels | Add a `tags` column (JSON array). Free-form labels like `experiment`, `archived`, `demo`. Filterable from the list view. Lets the user keep stale conversations without `list` becoming visually noisy. |
| Low | Enhancement | Web UI: editable topic + delete-conversation button | The seed-conversation form covers creation; round it out with the inverse — a pencil icon to rename a topic (typos happen) and a delete button gated behind a confirm. Delete should cascade messages. |
| Low | Enhancement | Web UI: per-message permalinks and copy buttons | Each message gets `#msg-<id>` as a stable anchor and a small "copy link" / "copy text" button on hover. Makes it trivial to point someone at a specific exchange in a long transcript. |
| Low | Enhancement | Web UI: keyboard shortcuts | `j` / `k` to navigate between messages on the detail page, `g` then `c` to jump to the conversations list, `/` to focus search, `?` to show a shortcut help overlay. Cheap once the basics are in. |
| Low | Enhancement | Web UI: empty- and error-state polish | When `db/chat.db` has zero conversations: a friendly empty state with a "Seed your first conversation" CTA pointing at the new seed form. When a conversation id 404s: a clear message instead of a Starlette stack trace. |
