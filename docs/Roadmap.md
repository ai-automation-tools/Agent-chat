| Medium | Bug | **The sidecar's push watermark can outrun a local edit and skip it forever** | **(2026-08-27)** `sync_once()` in `scripts/db_sync.py` ends every tick with `conversations_updated_after = max(old, max pushed updated_at, server_time)`. The `server_time` term is the anti-ping-pong guard — a row just *pulled* has `updated_at <= server_time`, so folding it in keeps the next push from echoing it back. But it also means the watermark marches forward on the **remote** clock whether or not anything was pushed, so any local write whose `updated_at` lands behind the last tick's `server_time` is never seen by `read_changed_conversations()` — and never will be, because the watermark only grows. Hit for real re-titling #54/#57/#58: three `UPDATE`s with a fresh `updated_at`, watermark already past them, no push logged, mirror unchanged. Recovered with a one-off `--once --state-file` run against a rewound copy of the state. **Two things make it easy to hit:** local and Fly clocks need only differ by a second or two, and two sidecars sharing one `.sync-state.json` (a scheduled one plus a hand-started one) race each other's writes. **The fix is probably to stop mixing clocks in one watermark** — track the pull cursor in server time and the push cursor in local `max(updated_at)` alone, which is what `pulled_updated_at` already does separately. Add a test that writes a row with a stale-but-unsynced `updated_at` and asserts the next tick pushes it. Worth a `--force-push` / `--rewind` flag either way, so recovery doesn't mean hand-building a state file. |
